# Security

This service performs behavioural monitoring of individual employees. That is
sensitive by nature, so this document states plainly what the deployed demo
does and does not protect, and what a real deployment would need.

## What the data is

The public deployment serves the **CERT r4.2 Insider Threat Test Dataset** —
synthetic data generated by Carnegie Mellon's Software Engineering Institute
for research. The 4,000 "users" are fabricated. **No real person's activity is
exposed by this demo**, which is why it runs open to the internet.

Pointed at real logs, every consideration below stops being optional.

## Controls

All of these are configured by environment variable, so the posture changes
without touching code.

| Variable | Default | Effect |
| --- | --- | --- |
| `API_KEYS` | unset | Comma-separated `name:key` pairs, one per analyst. When set, every data endpoint requires a matching `X-API-Key` header. Unset leaves the API open. |
| `RATE_LIMIT_REQUESTS` | `120` | Requests allowed per client per window. `0` disables limiting. |
| `RATE_LIMIT_WINDOW_SECONDS` | `60` | Length of the window. |
| `CORS_ALLOW_ORIGINS` | unset | Extra allowed browser origins, comma-separated. |

**Authentication.** Each analyst gets their own named key rather than a
service sharing one secret; that name is what ties an audit log entry to a
person. Key comparison uses `secrets.compare_digest`, so a wrong key cannot be
recovered by timing the response. `/`, `/docs`, `/redoc` and `/openapi.json`
stay reachable without a key so health checks and discovery keep working.

**Rate limiting.** Fixed window per client. Behind a reverse proxy the socket
address is the proxy, so the first hop of `X-Forwarded-For` is used instead.
The limiter's own bookkeeping is capped at 10,000 tracked clients so that it
cannot itself be turned into a memory-exhaustion vector.

**Response headers.** `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and
`Cache-Control: no-store` are set on every response, including errors —
`no-store` matters because responses contain per-employee detail that should
not sit in a shared cache.

**CORS.** Origins are allowlisted explicitly. The API never responds with
`Access-Control-Allow-Origin: *`.

**Read-only.** There is no write path. The service loads a precomputed parquet
and serves it; no endpoint mutates state, and there is no database, no user
input reaching a query engine, and no file path derived from a request.

**Audit log.** Every read of `/user/{id}/timeline` — the endpoint that exposes
one employee's full behavioural history — is logged as a JSON line to stdout:
timestamp, requesting client (IP, or the first hop of `X-Forwarded-For` behind
a proxy), the analyst name resolved from `API_KEYS` (`null` if auth is
disabled), the user ID looked up, and whether it existed. Render and most
hosts capture and retain stdout, so this needs no extra infrastructure to
query "who looked up whom." `/stats` and `/threats` are not logged since they
don't target a specific individual.

## Known limitations of the public demo

Stated honestly rather than papered over:

- **The hosted demo is unauthenticated.** `API_KEYS` is not set on it, because
  the data is synthetic and a judge should be able to click a link. This is a
  deliberate configuration choice, not a missing feature.
- **No transport security of our own.** HTTPS is terminated by the host.
- **Rate limit state is per process.** It is correct for the single-worker
  deployment used here. Multiple instances would each keep their own counters,
  so a shared store (Redis) would be needed to enforce a global limit.
- **No authorisation model.** Each analyst has their own key, and that
  identity now reaches the audit log, but there are still no roles or scoping
  — any valid key can read every user's data. Real use needs per-analyst
  restrictions (e.g. by department), not just per-analyst identity.
- **Key distribution is manual.** Keys are minted by hand and pasted into
  `API_KEYS`; there's no self-service issuance, rotation, or revocation flow.
  Removing one analyst means editing `API_KEYS` and redeploying — other
  analysts' keys are unaffected, but there's no way to do it without a
  deploy, and no expiry if a key leaks.

## Enabling authentication

```bash
KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export API_KEYS="alice:$KEY"
uvicorn src.api:app --port 8000
curl -H "X-API-Key: $KEY" http://localhost:8000/stats
```

Add more analysts as additional comma-separated `name:key` pairs, e.g.
`API_KEYS="alice:$KEY1,bob:$KEY2"`.

Because the dashboard is a static site, any key shipped in its bundle would be
readable by anyone who views source, so it never lives in the build. Instead
the dashboard prompts the analyst for the key at runtime the first time an API
call comes back 401, and keeps it only in that browser tab's `sessionStorage`
— gone when the tab closes, never written to the compiled JS. A "Change API
key" control appears once one is set. This is a stopgap, not a substitute for
real per-analyst auth: everyone shares the same key, and anyone who has it can
paste it into any browser. A production deployment still needs a
token-issuing backend or a proxy that attaches the key server-side.
